## Before you fill this in: two conventions that matter more than the content

### 1. Capture meaning, not just facts

The Memory Base exists so Claude can know you as a person, not merely as a list of attributes. Record what a fact *reveals*.

- Weak: "Lives in [town]."
- Better: "Chose a 1906 house in a historic walkable town over a newer place elsewhere, which says something about valuing craft and community over convenience."

The second version lets Claude anticipate. The first only lets it recite.

### 2. One section is canonical for anything that can change

**Current State is canonical for all mutable facts.** Role, live projects, open questions, current capability. Purpose & Context carries durable background. On the Horizon carries forward commitments. Neither restates a current-state claim.

This is not tidiness. It is the single most valuable structural lesson in this system, and it was learned the expensive way: a standing finding turned out to be wrong and was found in three sections at once. It had been corrected in one of them weeks earlier. The other two still read as authoritative, were loaded at every session start, and the document's Last Updated date said it was current.

**A fact restated in three places gets corrected in one and stays wrong in the other two.** Related discipline, in the core protocols: before correcting any load-bearing fact, search the whole document for the *old* wording, not the new one.

## What does NOT belong here

Putting these in the Memory Base makes it long, stale, and less likely to be read carefully.

| Content | Where it goes |
|---|---|
| Detailed project specifics | Project pages |
| Session-by-session work logs | Session summaries |
| Transient tasks and deadlines | Tasks database |
| Research details and citations | Research library |

**The test:** the Memory Base captures *who you are* and *how you work*. Project pages capture *what you are working on right now*.

## Usage Guidelines

### Loading
Load at the start of every session for persona context. Procedure lives in the protocol documents, not here. Keep it that way: when both a memory document and a protocol document describe the startup sequence, they diverge, and it is not obvious which one a session followed.

### Updating

Update when major milestones are reached, projects start or finish, frameworks emerge, or working patterns change.

**Two habits worth adopting from the start:**

**Update the Last Updated date in the same edit as the change, not afterwards.** Treat it as a gate: do not report the update as done until the date is updated. A stale date on a changed document is worse than no date, because it actively asserts currency.

**Record what changed and why, not just that something changed.** A short note per revision, kept in reverse chronological order, turns the header into a decision log. Months later the useful question is rarely "what does this say" but "when did we start believing this, and what prompted it". That is also how you notice a belief that has never been re-examined.
